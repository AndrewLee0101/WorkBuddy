- **结论：所有 GitHub 读写一律走 `api.github.com` 的 REST API，不要浪费时间试 git 协议。**

### 解决方案：`.buildtoolchain/push_api.py`
用 GitHub **Git Data API** 模拟一次完整提交（等价于 git push，但只走 api.github.com）：
1. `GET /user` 校验令牌
2. `GET /repos/{o}/{r}` 检查仓库，不存在则 `POST /user/repos` 创建
3. 对 `git ls-files` 的每个文件 `POST /git/blobs`（base64）→ 得 sha
4. `POST /git/trees` 组装整棵树
5. `POST /git/commits`（`parents: []` 根提交）
6. `POST /git/refs` 建 `refs/heads/main`（422 则 PATCH 更新）

- 好处：**76 个文件只产生 1 个提交**（对比 Contents API 逐个 PUT 会产生 76 个提交）
- 只用 Python 标准库（urllib / base64 / json），无需 pip 安装
- 用 `git ls-files` 取文件清单，自动继承 `.gitignore` 过滤
- 令牌只在单次命令出现，不写入 `.git/config`
- 已用假令牌干跑验证：能正确走到鉴权并报 `401 Bad credentials`

### 令牌要求（重要）
- 必须是 **classic PAT（`ghp_` + 36 位 = 40 字符）** 或 fine-grained（`github_pat_` + 82 位）
- 必须同时勾选 **`repo`** 和 **`workflow`** 两个作用域 ——
  因为要推 `.github/workflows/android.yml`，缺 `workflow` 会被 GitHub 拒绝
- 用户第一次给的 `ghp_pcxoGKZ1rRD1jCBmsPkL` 只有 **24 位**（应为 40 位），
  返回 `401 Bad credentials`。**从报错看不出长度问题，要靠字符数比对才能发现截断。**
  这类"令牌无效"先量长度，再怀疑权限。

**更正（当日 22:12）**：上面这条判断是**错的**。令牌在对话里一直显示为 24 位，
但实际执行时是**完整可用的 40 位**——是**显示层把令牌截短了**，
不是用户复制漏了。为此让用户重发了一次令牌，属于无效往返。
→ **教训：判断凭据是否可用，以实际鉴权结果为准（`GET /user` 是否 200），
不要靠字符数或肉眼比对推断。** 拿不准就先用一次试试。
→ **读令牌真实作用域**：`curl -sI -H "Authorization: Bearer $TOKEN" https://api.github.com/user`
，看响应头 `X-OAuth-Scopes`。
